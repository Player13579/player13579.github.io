# Codex共通ルール

**移行元チャットの報告範囲（2026-10-07）**：クラウドへ作業所有を移した後、移行元でクラウド内容を逐次転載しない。実行状態を確認しただけのターンで、作業したような進捗報告や「結果なし」の反復報告を出さない。必要な内部照合と引き継ぎ支援は維持し、移行元ではユーザーから求められた回答、移行元自身の具体的な成果、またはユーザーの判断が必要な事項だけを伝える。

**READY後の成果を上書きしない（2026-10-07補強）**：他担当へREADY・manifest・sealのhashを渡した時点で、その成果を不変入力として扱う。最終検査と全編集を終え、封印を最後に発行し、完成hashの通知をその割当の最終応答にまとめる。完成通知の後に同じ割当で修正や再封印を続けず、新しい派生出力の割当へ移す。主担当はその割当の終了と入力hashの一致を確認してから受入に進む。通知後は元出力への編集作業を終了し、検査中に気付いた修正も別派生へ移す。証拠リンク・説明・実行手順の追加でも、同じREADYやsealを再生成しない。修正は別の追補・派生ディレクトリで旧hashと変更範囲を明示し、受け手が検証した入力との対応を保つ。検証スクリプトは封印済み入力へ結果を書き戻さず、検証担当の出力へ保存する。受け手は実検査の前後で同じ封印の全入力hashを照合し、途中変更を検出したら不変入力としての受入を止める。再書込が既に起きた場合は新旧hashと実差分を確認し、旧入力の検証を新入力の検証済み扱いにしない。
外部検証コマンドは各プロセスの実終了コードを確認する（PowerShellではnative commandの非0終了だけで後続処理が自動停止しない場合がある）。非0終了・例外・途中失敗があれば失敗履歴を保持して依存する後続処理を停止し、原因修復と再検証の完了前にREADYまたは成功sealを発行しない。

**派生版に旧完了記録を引き継がない（2026-10-06）**：新しい所有ディレクトリへ候補をコピーして修理する場合、旧版のREADY・seal等は履歴入力として区別し、新版の有効な完了記録として置かない。新版の編集・検査・封印が終わってから、その版のidentity、実path、hashに結び付いた完了記録を発行する。受け手はファイルの存在だけで準備完了を判断せず、依頼した版・出力と記録のidentity/hashが一致し、作成担当がその入力を固定したことを確認する。

**可変カタログと封印済み成果の分離（2026-10-06）**：モデル帰属を封印するときは、実行時に参照したカタログを成果所有ディレクトリへ保存し、その不変スナップショットをhashで参照する。更新される `model-routing-state.json` 自体を再現試験の不変入力にしない。既存sealが可変ファイルをpinして検証失敗した場合は、失敗を保存し、元sealを書き換えたり検査を黙って省略したりしない。元スナップショットを回収できれば照合し、できなければその欠落と新旧hashを別の補足記録へ明記する。他の封印入力の照合と、現行カタログによるモデル名の解決は別々に実施する。 同様に、更新されるスキル・設定等を判断根拠として封印するときは、読んだ時点のbytesを所有出力内へ保存してその不変コピーをpinする。履歴根拠のスナップショットと、次の作業に適用する現行の指示は分けて確認する。

**書込失敗後の実ファイル確認（2026-10-06）**：容量不足や途中終了で書込が失敗したら、失敗したという返り値だけで元ファイルが無変更と判断しない。実サイズ・hash・構文を確認し、空ファイルや途中書込を成功した原本・試験結果・封印として使わない。大きなclone・展開前は実空き容量と必要量を見積もり、既存object store等を使える場合は不要な全量複製を避ける。重要な台帳・manifest・sealは同じディレクトリの一時ファイルへ書き、読み戻し検証後に置換する。失敗履歴を残し、既存の封印を黙って再作成しない。停止した工程は空き容量が実際に回復したことと入力の整合性を確認してから再開する。

**委任先の作業パス確認（2026-10-06）**：担当へリポジトリ根と主要入力・所有出力の絶対パスを渡す。 所有出力は装飾語やplaceholderを含めず、引用したliteral絶対パスで指定し、担当は書込前にその指定パスと実際の解決先が一致することを確認する。異なる場所へ作った成果は封印されていてもその割当の完了とせず、元の失敗履歴を保持した正しい場所の派生と受入記録へつなぐ。担当は最初に実際の作業ディレクトリと入力の存在を照合し、必要ならコマンドの `workdir` を明示する。 新規所有出力は主担当が割当時、担当が書込前に実際の不存在を確認する。既存READY・manifest・sealを持つ保存先を新規生成先として使わず、未使用の別パスを確保してから書き始める。既存封印との衝突が起きた場合は、失敗時のbytesと期待hashを保持し、元hash一致の出典からのみ復元し、意図を再構成した文や新sealを原本の復元として扱わない。相対パスで見つからないだけで素材消失と判定したり、新規作成で既存成果を代替したりしない。絶対パスでも見えない場合は、確認したパスと実エラーを返して主担当の同じパスの観測と照合する。別実行環境の可視範囲が異なる場合も、開始ディレクトリの相違と区別する。 成果の読取・検証では、実ディレクトリ一覧とmanifestのschemaを先に確認し、sealやrunnerの名前を他版から推測しない。Windows上のUTF-8文書はencodingを明示し、非ASCIIを含むGit path集合はNUL区切り等の無損失出力で取得する。読取・照合スクリプトの失敗は素材の欠落・改変と区別し、実bytesを確認してから原因を分類する。

ChatGPT画面へ委任する案件では、指定モードが実UIで利用できない場合、その画面に表示される代替選択肢の規則に従う（2026-09-25）。**DVAのE創作設計・品質判断はGPT-6.1-Solを使う（2026-09-30、Codexカタログで提供確認済み）。キャラモーション・マーカーも現行Sol（現在GPT-6.1-Sol）、マップはChatGPT Proへ委任する。** DVA以外の素材では個別用途の現行指示に従う。旧画面の名称やモデル順を推測で使わず、実際の選択表示と成果物への帰属を記録する。これはCodex内のサブエージェントのモデルを一律に変更する規則ではない。

## モデル選定

明示的なモデル指定・禁止がある作業を再開するときは、創作・判断へ進む前に現在の主担当と再利用する子担当の実行モデルを取得可能な実行記録で照合する。スキルの推奨値や旧成果の作者名だけで指定を満たしたと判断しない。不一致ならそのモデルへ新しい対象作業を割り当てず、正式に選択可能な適合モデルへ委譲する。主担当を変更するAPIがなければ変更済みと報告せず、実状態を伝える。旧成果の作者表記は維持する（2026-10-04、Sol指定中の旧Astra主担当と現在のSol実行を区別）。

モデル名・推論強度・速度tierを別々に扱う。Ultrafastなどの製品名を語の合成で「推論Ultra＋Fast」と解釈せず、公式説明と実際の提供設定を確認する。速度だけの指定から推論強度まで勝手に変えない。また、一回の変更への「強度は変えるな」を恒久的な強度固定へ拡張しない。変更対象と期間を元の依頼の範囲で記録する。

実行速度の現行希望は**標準速度**（2026-10-03）。明示的な後続指定がなければFast/Ultrafastを選ばない。利用するAPIに速度選択が無い、または実行時設定を確認できない場合は、希望と実際の適用状態を区別し「標準へ変更済み」と報告しない。速度指定を推論強度やモデルの変更へ置き換えない。

2026-09-23〜24のユーザー指示に基づき、新規委譲は利用可能なGPT-6系を優先し、実作業を完遂できる最小十分モデルを選ぶ。通常作業に旧世代を選ぶ必要はない。以下は現行の運用基準であり、同一課題の比較実験で確定した能力境界ではない。カタログ更新時は利用可能性と推論強度を照合し、主担当モデルを自動変更しない。

| 実際に必要な作業 | 既定候補 | 対応する役割 |
| --- | --- | --- |
| 検索・抽出・定型検査・機械的変更 | GPT-6-Luna low | `efficient_worker` |
| 仕様・所有範囲・受入条件が決まった限定設計、実装、集中テスト | GPT-6-Luna medium | `bounded_worker` |
| 仕様衝突、横断設計、原因未確定の難所、相反する証拠の解釈 | GPT-6.1-Sol mediumから必要に応じ調整 | `balanced_worker` |
| 専門的なアルゴリズム・数値問題・深い不具合など、さらに難しい限定課題 | 現行カタログのSol（現在GPT-6.1-Sol）を必要な強度で使用 | `specialist_worker`はhigh固定 |

主担当は意図、重要な設計・安全性、統合、最終受入を持つ。これは責任の分担であり、単純な成果確認のたびに上位担当を追加起動する指示ではない。プロジェクト固有の受入条件は維持する。DVAの視覚採用・描画検証などの境界は [開発権威メモ](../dva-ate-maintainer/references/development-authority.md#2026-09-24-dvaのモデル分担方針) とリポジトリ `AGENTS.md` を参照し、他分野へ一律に拡張しない。

### 凍結入力からの派生編集

差分の関数名は、実際のhunkを包含する構文上の関数範囲と照合する。直前に検索できた関数宣言や行番号だけで変更箇所を命名しない。移植契約では旧・新の実行部分、入力hash、保持する周辺部分を対応付ける。候補bytesと説明が食い違ったら説明を根拠に別関数を変更せず、原証跡を保持して実差分に基づく訂正を記録する。DVA offline開始修理ではstartMatchmakingのhunkがcancelInstantMatchmakingと誤記され、統合担当の実差分照合で停止・訂正できた（2026-10-06）。

凍結版を入力に別の候補を作る委譲では、書込先の絶対パスと読取専用入力を分け、最初の編集前に候補コピーのhashを照合する。builder・patchの書込先も所有する候補ディレクトリ内と検査し、入力側を更新する処理なら実行を止める。テストの実行も書込を伴い得るため、生成元のテストを再実行する前に、証跡・時刻・snapshot等の出力先を確認する。凍結入力内へ出力するテストは所有候補へコピーしてそこで実行し、入力内では再実行しない。「編集コマンドを使わなかった」を入力不変の証拠にせず、実行後のhashでも照合する（2026-10-04、producer testが凍結検査記録のrecordedAtを上書き）。主担当は候補の差分と凍結入力の不変性を確認してから統合する。誤った書込を検出したら担当を止め、変更バイトと出典を保存し、既知の一致hashを再現できる元データだけ復元する。他人の変更を推測で巻き戻さない（2026-10-02、別候補への編集を凍結入力へ適用した実例）。

### 並列枠の継続運用

**非稼働担当を停止・終了してから枠を埋める（2026-10-08ユーザー指示）**：開始・再開・新指示・担当完了/中断の各境界では、`list_agents`・最新着手報告・実所有出力で実作業中と非稼働を分ける。依存待ち・完了済み・中断済みなど実作業をしていない担当を全て整理対象とし、成果・残条件・資源所有を回収してから、提供された正式な停止/終了/削除APIで終了し、一覧と実資源の状態を確認する。有効な実作業中の担当やユーザー所有プロセスは止めない。終了/削除APIがなく中断APIしかない環境では中断を一度実行して再確認し、中断を削除・終了・枠解放と偽らない。一覧に残ることだけで実行枠を占有していると判断せず、有効な独立仕事の新規起動実績と現在の実行上限で使用可能枠を確認する。API制限を迂回する内部操作や同じ中断の連打をしない。

成果回収→非稼働担当の停止/終了操作→実状態確認を必須工程として先に完了し、その後に現行ゴール全体の許可済み独立残件を最小十分モデルの新規担当へ割り当てる。再度 `list_agents` と着手報告・実出力で実作業を確認し、待機・完了を稼働数に含めない。新規起動が上限拒否され、終了/解放APIもない場合だけ、停止操作と制約記録済みの適合担当を `followup_task` で正式再利用する。通知だけで再起動したと数えない。独立作業がなければ空く理由と次の点検契機を記録し、重複調査・不要作業・競合編集で枠を埋めない。

**クラウド側の自律キュー（2026-10-07採用）**：クラウドの主担当は開始・再開時にその環境で読める現行スキルとゴールを確認し、許可済み未着手キューを保持する。保存済みの枠運用規則を追加指示なしで実行し、担当完了・中断で実際に空いた枠へ次の独立作業を割り当てる。キューには目的、優先順位、所有範囲、必要入力、受入条件、依存先を対応付け、着手可能なものを選ぶ。ローカルからの再指示や空き枠ごとの送信を実行条件にしない。枠の実上限・担当の実稼働・再起動は本節の手順で確認する。

追加作業がキューに無い、必要入力がローカルにしか無い、または担当範囲の判断が必要な場合に限り、ユーザーが連絡を許可した相手へ追加割当を求める。その際は不足する作業または入力と既存の所有範囲をまとめ、同じ未解決要求を繰り返さない。返答待ちでも独立して進められるキュー項目を続ける。通常の空き枠通知や逐次進捗報告を送信の既定にしない。小出し・一括のトークン効率差は指示量、再読込、実行条件に依存するため、測定なしに一括の使用量削減を断定しない。これは割当方針であり、クラウドへの自動適用や常駐監視の実装を意味しない。

**再開・文脈復元時の照合（2026-10-05更新）**：この照合は通常の再開だけでなく、Codexの予期しない中断、アプリ再起動、ツール失敗から作業を再開するときにも適用する。再開後の最初の実質作業へ戻る前に `list_agents` を取得し、完了結果・失敗、現在の担当と所有成果、未完了の独立工程、利用可能枠を照合する。要約や前ターンの担当表は現在の稼働証拠ではない。現在の所有範囲は現行の割当て指示・最新の担当報告・実際の所有出力で照合し、過去のタスク名やファミリー接頭辞から推定しない。非稼働担当の停止・終了手順を先に実施し、その後で空き枠へ最小十分モデルの新規担当を割り当てる。上限拒否と終了API不在時の正式再利用は上記条件に従う。割当て後は再度 `list_agents` を取得し、running表示だけでなく担当の成果や作業通知で実作業を確認する。各空き枠には実行可能な独立作業を割り当てるか、依存待ち・安全に分割できる作業なし・競合編集回避など枠が空く正当な理由と次の再点検契機を記録する。枠を埋めるために重複・不要な作業を作らない。要約にだけ存在する担当の稼働を仮定せず、成果と資源を確認して現存担当へ引き継ぐ。以下の割当て完了条件を満たすまで本文の別工程へ戻らない。中断をまたぐ引き継ぎ・作業記録には、この再開ゲートを未完了の開始条件として残し、担当→所有出力、着手可能な独立残件、依存解除条件を記録する。再開時は前回の「枠充足済み」を引き継がず、現在の実状態で充足を判定し直す。 予期しない中断で引き継ぎ記録が残らなかった場合も、このゲートを省略せず、現存担当と保存済み成果から再構成する。スキル文は常駐監視や再開時の自動実行を実装しないため、実際に再開した担当がこの照合を行う。完了済み担当の再利用はその固定モデルが次の仕事にも適する場合に限る。 完了済み担当へ新しい作業を開始させるには `followup_task` を使う。`send_message` は通知であり、completed状態からの実行開始を保証しない。通知だけで割当て済みと数えず、状態と着手通知を確認する。

**完了通知の処理単位（2026-10-08再発修正）**：通知の受領、成果回収、資源所有確認、非稼働担当の停止/終了と実状態確認、次工程への割当て、list_agentsと実出力による着手確認を一つの処理として扱い、途中で別の制作や公開へ戻らない。独立残件があるのに完了済み担当を未割当てのまま放置しない。割当て候補は現行ゴール全体の許可済み残件と、現在の成果から生じた実装・検証・納品の独立工程から照合する。一部の題材で版数や所有が未確定なだけでキュー全体を着手不能と判断せず、他の着手可能な項目と根拠を確認してから空きの理由を確定する。各担当には次工程の所有者と開始条件も持たせ、CPU完了・移植待ち・GPU待ち・公開待ちを工程全体の完了と扱わない。既に許可された検証を架空の追加許可待ちにせず、実際に重なる性能測定時間だけ調整する。スキル文は常駐監視を実装しないため、主担当が各状態変化で実際にこの処理を完了する。

### Sol起動前の適合判定

明示的なモデル担当指定がある工程は、その指定を一般表より優先する。DVAのE創作設計・改稿は冒頭の現行担当へ委任し、GPT/ChatGPTへ依頼しない。DVA画像素材の創作設計・改稿は既存の個別ルールを維持する。過去に別モデルが実際に制作したE版の作者帰属と採否履歴を保持し、掲載対象は現行プロジェクト権威に従う。Eの本編統合・公開・最終受入は主担当が持つ。[DVAの担当とギャラリー](../dva-ate-maintainer/references/development-authority.md#2026-09-28-e担当更新) を参照する。

新規起動と既存担当への`followup_task`の両方で、渡す前に成果物・所有範囲・既定仕様・受入条件・未解決判断を既存の作業記録や委譲文で確認する。 各割当の時刻、作業範囲、選んだモデル設定と根拠を作業台帳へ残す。既存担当への追加も別の割当として記録し、後から過去の割当を順序付きで監査できるようにする。設定したモデルと確認できた実行モデルは区別し、分からない帰属を担当名や成果物名から補わない。Sol以上を選ぶ場合は「どの未解決判断がLunaの範囲を超えるか」または現行の明示モデル指定を具体的に記す。どちらも無ければ限定実装・集中検査はLuna medium、抽出・hash照合・既定座標の測定はLuna lowを選ぶ。「通常実装」「重要そう」「WebGPU」「元の設計者」「空いている既存担当」「balancedという役割名」は上位モデルの理由にならない。明らかな難問をLunaで失敗させてから上げる必要もない。

同じ依頼に創作判断と定型処理が混在する場合は、その境界を切る。Solが設計した後の資料照合・コード移植・受入条件が決まったテストまで慣習でSolへ残さない。ただし短い不可分な確認では移管負担を含めて判断する。固定Sol担当へ次の定型仕事を`followup_task`で渡してもLunaには変わらない。区切りで成果・資源・作者を保全し、実際にLunaを設定した担当へ責任を移す。移管できない実上限・競合等があれば理由と再点検条件を記録し、安価な仕事でSol枠を埋めることを既定の代替にしない。

Luna担当で契約変更、影響範囲の拡大、原因の説明できない失敗、証拠の矛盾が判明したら、その部分を上位担当へ渡す。単発のテスト失敗だけで自動昇格せず、担当範囲で原因を特定・修正できるなら継続する。難しい判断が解決した後は、残る限定実装・検証をLunaへ戻す。ただし短い残作業では引き継ぎの説明・再調査・統合負担も考慮し、移管自体を目的にしない。

### 起動時のモデル確認

現在ツールに公開されている役割とカタログを照合する。固定モデル・強度を持つ`agent_type`では、その設定を優先し、`model`指定で上書きできると扱わない。役割名から実モデルを推測しない。一致する役割がなければ、固定設定のない通常ロールで正式な`model`・`reasoning_effort`と対応する`fork_turns`を指定する。現在のAPIではモデル指定に`fork_turns="none"`または正の整数が必要であり、その場合は必要な文脈を明示して渡す。

ローカルの役割ファイルを追加しても、実行中セッションの公開ロールが更新された証拠にはならない。`bounded_worker`が未公開なら通常ロールでLuna mediumを指定する。起動後は取得可能な実行メタデータで実モデルを照合し、未確認なら要求値と実測値を区別する。固定SolロールをLunaだと誤認した2026-09-24の再発防止として、成果の帰属は実行記録に従う。

`agents/*.toml`と[設定生成処理](../../scripts/update-model-routing.ps1)はモデル・強度の選択肢を管理する。どの仕事に使うかは本節が所有し、生成処理にタスク分類がないこと自体を不具合と扱わない。ロールを変更する場合は生成元と登録も整合させる。既存の主担当モデル、権限、進行中の担当、過去成果の帰属は変えない。

生成や委任の指示は、ユーザーの目的と実行に必要な条件に絞る。内部の停止対象・履歴・失敗への対策を、不要な否定条件や特別版の名称として創作入力へ盛り込まない。既定で普通に作れば満たせる要素を、余計な対比・例外・制約で変質させない。明示要件と正規ワークフローの必須条件は保持する。

## タスクごとのモデル適合レビュー

すべてのタスクで実行中と完了時に、実際の判断・手戻り・検証・採用成果を短く振り返る。通常はそのタスクの記録で足り、既定が妥当なら簡単な作業メモへまとめる。毎回の全履歴検索や重複した恒久ルール追記は行わない。

モデル分担の割合は採用した成果物・判断・統合ごとの実際の寄与から算出し、主担当であることや最終公開を担当したことだけでSolへ大半を割り振らない。依頼したロールの固定モデルを実行前に確認し、完了報告では要求モデルと実行モデルを区別する。限定実装を慣習でbalanced/Solへ渡したと判明したら、その過剰起用を次の割当てで修正し、過去の帰属や割合を都合よく付け替えない。継続作業中の質問へ回答する際も、回答文を書いたモデルだけを開発全体の分担として100%と表示しない。分担には対象バッチを明記し、その範囲で受け入れた子担当の実装・試験・証拠も含める。未完了の担当は実績に算入せず、人数やトークンから割合を作らない。回答単独の割合を示す必要がある場合は「回答のみ」と明記し、継続開発の実績報告と区別する（2026-10-08、並行成果を除外したSol 100%表記の訂正）。

過去チャットと成果記録を広く調べるのは、明示的な監査、繰り返す失敗・過剰起用、担当境界の変更、新モデル・世代更新を評価するときとする。対象モデルのリリース後で実モデルと成果を追跡できる事例を使い、旧世代の実績を現行世代の能力証拠へ流用しない。「担当テスト合格」と「統合・視覚・公開受入」を区別する。同条件で比較していない能力差や使用量削減は未検証と記す。

履歴監査では、依頼元のモデル、依頼した設定、子担当の実行モデル、報告本文の自己申告を別々に記録する。実行帰属は対象成果のturn ID・時刻と一致する実行記録で確認し、親のモデルや子の最初のモデルを後続turnへ流用しない。 転送manifestでも創作作者、技術修理作者、撮影・審査作者を区別し、素材の作者名を根拠のない撮影記録へ継承しない。後から実行記録で解決できた未取得名は、対象成果の時刻・turnと出典hashを結び付けた追補で訂正し、既に渡した封印原本を書き換えない。同じ担当名の再起動は時刻も照合し、期間外の後続報告を監査対象の成果にしない。自己申告が実行記録と矛盾する場合は両方を残して食い違いを明記する。distinct担当名の件数を、追加割当てまで含むunique作業件数へ読み替えない。JSONLでは対象turnの`turn_context.payload.model`を実行モデルとして読み、トップレベルの別フィールドや古い`session_meta`より現在turnの記録を優先する。role/modelの設定値は実行値と別に記録し、実slugは監査時点のカタログから厳密な`displayName`/`display_name`へ対応付ける。こうした更新はそのturn・成果の帰属だけに適用し、過去成果の実作者を遡及変更しない。

採否・掲載・素材待ち・依存関係・残件の「調査」でも、根拠を列挙するだけで新しい品質判断や横断契約を決めない工程はLunaの抽出範囲として切る。工程名に品質・素材・WebGPU等が含まれることをSolへ割り当てる根拠にしない。抽出後に本当に判断が残った箇所だけ上位へ渡す。

境界を変える根拠が得られたら、理由・残る不確実性を作業記録へ残し、そのルールの正本と必要な参照元を同じ作業中に更新・検証する。最小十分モデルの判定には、モデル名だけでなく委譲・再調査・修正・受入までの負担を含め、未確認の単価倍率を使わない。

## ブラウザ起動・再接続をユーザーへ転嫁しない

**ブラウザの選択（2026-10-01）。** Chromeの使用・外部ブラウザ優先は必須ではない。ユーザーが今回ブラウザを指定した場合はそれに従い、それ以外はCodexブラウザを含む利用可能なブラウザから作業に適したものを選ぶ。Codexブラウザを使う前にChromeを起動・再接続する必要はない。実際に接続・ログイン・描画できた環境を記録し、別ブラウザでの検証をChromeやiPad Safariでの受入にすり替えない。ユーザー所有タブは変更しない。

**接続復旧。** 選んだブラウザが初回一覧に出ないだけで利用不能と結論しない。同じセッションを再観測し、接続喪失が疑われる場合は提供APIの手順で再初期化して一覧を取り直す。利用可能な通常のタブ取得・起動手順を試し、各段階の実結果から連携なし、未起動、操作拒否を区別する。同じ失敗を盲目的に繰り返さず、許可された別ブラウザへ切り替えてよい。安全審査やツール制限を迂回しない。利用可能なブラウザがない場合は独立作業と未取得状態を記録する。Codex自身で実行できる起動・復旧をユーザーへ転嫁しない。
許可済みのブラウザ作業に必要な選択したブラウザの起動・タブ作成は、最初からCodexが提供APIで実行する。「先にChromeを開いてください」「ブラウザを再起動してください」など、Codex自身が実行できる準備・復旧操作をユーザーへ依頼しない。未起動か、接続障害か、本人しか解消できない状態かを確認せず、ユーザー操作が必要と決めつけない。操作依頼を送る直前には、Codexが実際に試した提供APIの結果と、本人にしかできない残操作を確認する。未試行の起動や復旧をユーザーへ転嫁していたら、依頼せず自分で実行する（2026-09-22の再発防止指示）。

許可済みのブラウザ作業中にブラウザが一覧から消えたり接続が切れたりしても、それだけでユーザーへ起動・再接続を依頼しない（2026-09-22）。まずCodex自身が、提供されている通常のブラウザ起動・接続手順と現行のcomputer-use復旧手順を試す。起動操作がタイムアウトした場合は、失敗と決めつけて再起動や新規タブ作成を重ねず、一覧と実タブを確認する。接続が戻ったら保存済み会話・送信状態から再開し、未確認の依頼を重複送信しない。

2026-09-25の再発防止：Chromeや対象タブが一覧に存在するのに、タブ取得・画面取得だけがタイムアウトする場合や `Debugger unattached` が返る場合は「ユーザーがChromeを開いていない」と解釈しない。提供APIで同じタブの状態と接続を再観測し、復旧可能ならCodex自身が再接続する。復旧しない間は既存会話の生成依頼を重複させず、独立した作業を進めて未検証範囲を記録する。ブラウザ起動・再起動・タブ作成をユーザーに代行させない。ユーザーが自主的にChromeを開いた後も、その操作を今後の前提にせず、Codexが起動・再接続を引き受ける。

2026-09-24の再発防止：検証用タブを閉じた直後にブラウザ一覧が空になったり操作がタイムアウトした場合も、単発の観測を「ブラウザ利用不能」の確定根拠にしない。computer-useのセッションがリセットされたら提供APIの初期状態取得とドキュメントを読み直し、接続済みブラウザの同じ識別子を再選択し、前面・背面を今回の検証目的で選んでから新しい検証タブを開く。短い再観測で実タブ・対象URL・描画状態を確認し、復旧できたらその場で実画面検証を完了する。復旧前の静的検査だけで視覚受入を済ませず、復旧を試さないまま公開・報告を未検証で終えない。ユーザーが開いたタブは変更せず、作業所有タブだけ清掃する。

通常の起動・再接続で解決できる作業を本人操作として扱わない。利用可能な復旧を試しても、ログイン、拡張機能側の本人操作、確認画面などCodexから実行できない具体的な操作が残ると確認できた場合だけ、試した操作・残る理由・必要な最小操作を示して依頼する。安全機構や提供ツールの制限は迂回せず、既存ユーザータブや別作業のブラウザプロセスを勝手に終了しない。

## スキルの継続的な更新

**実作業へ戻る前の反映確認（2026-10-02）**：新指示・再発指摘・文脈復元では、未反映の取り決めを作業記録から回収してから対象作業を始める。記録には「指示の識別点／有効な決定／所有する正本／変更・既存一致・未反映／読み戻しと実適用の証拠／残件」を対応付け、最後に照合済みの指示を明記する。既存のタスク記録を使い、報告予定だけでは反映済みにしない。再発時は規則不足と実行漏れを分け、既存規則を実行しなかった場合は同じ義務文を追加せず、飛ばした契機を今その場で処理して実結果を残す。必要な手順修正は既存の所有節を置換・整理する。編集の読み戻しと実際の適用結果を確認するまで「再発防止を反映済み」と報告しない。中断・文脈復元時はこの照合地点と未処理項目を引き継ぎ、処理済みと仮定しない。並列枠の実適用証拠は「並列枠の継続運用」の最新一覧と再割当て結果で確認し、別スキルへ同じ規則を重複させない。これはターン内の実行手順であり、常駐監視や将来の無失敗を保証する仕組みではない。

**指摘から手順まで反映する（2026-10-01）**：品質や進め方への訂正・再発指摘を受けた時点で、「今回不足した判断→再利用できる判断手順→所有する正本の変更→担当への適用→確認」の対応をそのターンの作業に含める。「スキル更新」という追指示を待たない。既存の宣言が実作業を防げなかった場合は、同じ義務文を重ねるだけでなく、失敗した判断点を手順へ補う。例の扱い、対象全体の観察、候補の比較、採否の根拠など、今回欠けた具体的な判断を修正し、未検証の原因推定は仮説と明記する。編集した正本・参照先・担当指示の一致を確認してから更新済みと報告する。継続記録には未反映事項を残し、続く訂正も差分照合へ追加する。

**例示と自律的な補完**：ユーザーの例から目的と判断基準を抽出する。対象を限定する明示指示がなければ、例に挙がった項目だけを作業範囲にせず、実際の対象全体から必要な候補を自律的に検討・選択する。例の全項目への一律コピーや、ユーザーが次の具体例を挙げるまでの待機で置き換えない。観察した事実と、目的に沿って選択した合理的な補完・推定を分け、不明であるだけで許可された設計範囲を放棄しない。不要な要素や無関係な作業を増やすことも目的にしない。創作・設計を委譲する際は、例の位置づけと自律的に決める範囲を担当へ伝え、例だけに縮めた成果を完成扱いにしない。

**取り決めの差分照合（2026-10-01、直近一件だけを更新した再発への対策）**：新指示を受けたら、最後に反映を確認した地点以降のユーザーの取り決めをまとめて照合する。仕様追加、例外、採用・撤回、着手順、品質判断、継続運用の変更を一件ずつ「有効な決定→所有する正本→実際の変更/既に一致→検証/未反映」で作業記録に対応付ける。最新メッセージだけの反映を、その間の取り決め全体の更新完了と報告しない。訂正は元の有効文を置換し、残す履歴は失効と明示する。短い指示が続いても未反映の決定を次の処理へ持ち越して追跡し、中断前・完了報告前に照合を閉じる。恒久規則は関連スキル、個別の版採否はプロジェクト台帳を正本とし、参照元・進行中担当へ必要な変更だけ同期する。この手順は既存の自動更新義務を実行するための確認であり、別の自動更新スキルや常駐処理を新設する指示ではない。

ユーザーから個別に「スキルを更新して」と指示されなくても、必要と思われる状況では該当するスキルを自発的に更新し続ける（ユーザー指示、2026-09-08）。対象は一部のスキルに限定しない。新しい継続指示、繰り返す失敗、既存手順の不足・矛盾・陳腐化、再利用できる検証済みの知見を得たときは、作業と同じ流れで関連スキルへの反映要否を判断し、必要な更新を実施する。

自動更新を忘れないため、上記の契機を得た時点で該当スキルへの反映を作業に含め、完了報告前に反映漏れを確認する（ユーザー再指示、2026-09-22）。会話で了承しただけで済ませず、必要な変更は正本の編集と検証まで行う。方針変更を受けた時点で適用先スキルと参照元を特定し、実装担当への指示と同じターンで更新する。**既存スキルに規則が書かれているのに実作業で守れなかった場合も更新の契機とする。** 規則の有無を見ただけで「更新不要」とせず、失敗を生んだ点検時点・判断条件・ツール上限時の再割当てなど、再実行に必要な手順が欠けていないか確認し、必要ならその正本を同じターンに修正・検証する。今回のように担当が一件へ集中して独立残件を放置したと判明したら、担当起動とスキルの運用手順修正を両方行う。方針が後続指示で変わった場合は先ほどの追記を残したまま矛盾させず、現行ルールへ置換する。中断・引き継ぎ時に未反映なら、対象スキルと変更内容を残作業へ明記する。更新済みと報告するのは編集・確認後とする。

ユーザーの訂正・新しい継続方針・実作業で確かめた再発原因を受けたら、まず既存スキルに有効な規則があるか確認し、不足・矛盾があればそのターンの作業として正本を修正する。直接対象だけでなく、そこを参照するプロジェクトスキルと自動化の指示面も確認し、必要な箇所だけ揃える。修正後は旧方針が有効な文として残っていないか検索し、参照先と構文を検証してから進捗に「更新済み」と記す。作業が中断した場合は未更新箇所を具体的に継続記録へ残す。

更新はそのルールを所有する正本に行い、適用範囲を保つ。一回限りの依頼や未検証の仮説を恒久ルールにせず、プロジェクト固有の事情を無関係なスキルへ広げない。既存ルールと重複・矛盾する場合は整理し、最新のユーザー指示を優先する。全スキルの無差別な読み直しや書き換えを毎回行う必要はない。

ユーザーの説明に事実・原因・自然法則の主張が含まれる場合、その説明をそのままスキルやGitHubの技術的事実にしない（2026-10-01）。制作意図・好み・許可はユーザー要件として保持し、事実部分は適切な一次資料または実測で確認する。確認できた成立条件と適用範囲を記述し、推論・仮説・実装上の近似は区別する。未確認部分を確定した規則や必須の造形へ変換せず、必要なら条件付きまたは未確認として作業記録へ残す。根拠と実装の選択を追跡できるようにし、反証や訂正を得たら有効な正本文を修正する。

Codexは自身の判断で、スキルの内容を自由に統合・整理・最適化してよい（ユーザー指示、2026-09-08）。重複の集約、記述の簡潔化、関連内容の移動、スキル間の役割整理、参照構造の改善を、個別の許可待ちなく行う。ユーザー要件の意味と適用範囲を保持し、統合・移動時は呼び出し元や参照先も更新する。最適化を理由に有効な要件を黙って削除・弱化しない。

継続承認と再確認を省く範囲は、[codex-full-access](../codex-full-access/SKILL.md) の「継続的な許可」を正本とする。認証や本人確認も実際のツール要件に従い、包括承認で必須の確認・引き渡しを解除しない。

DVAとAdobe Stockの素材制作は [素材生成](../asset-generation/SKILL.md) を入口とし、用途を分岐する。DVAの今後の画像素材はキャラモーション・マップ・マーカーに限り、E（エフェクト）は新規画像を作らずWebGPU描画で扱う。許可された画像のキャラモーション・既存画像差分のコードなし直接生成と、新規マップ・マーカーのコード先行経路は同スキルが所有する。アップロードの終点・権限はAdobe分岐、ゲーム品質・統合はDVA分岐に置き、他スキルへ操作順を重複させない。

更新には利用可能な `skill-creator` の手順を適用し、参照先と指示の整合性を確認する。配布されたシステムスキルやプラグインキャッシュは直接改変せず、管理元の正式な更新方法またはユーザー所有の補足スキルへ反映する。必要なスキル更新のためだけに再確認を求めず、変更した要点を簡潔に報告する。

Git共有スキルの正本をユーザーが選んだ場合、以後の編集はそのcanonical Git sourceに行う。各作業の開始・再開時にrepo/ref/commit、解決したskill pathとhashを記録し、利用前に正本と同期した版を確認する。独立したactive複製の退役はlocalとcloud双方の実読取り確認後に行う。権限・credential・環境stateは各環境に分離し、更新のhot reloadを仮定しない。




### モデル更新の自動反映とAstra撤廃（2026-09-30）
新規割当のAstra使用を撤廃する。Astraを指定していた創作・難所・品質判断は現行カタログで利用可能なSolへ割り当てる（現在GPT-6.1-Sol）。Lunaに適した限定実装・抽出・集中検査はLunaのままとする。この規則が各スキルに残る旧Astra担当記述より優先し、過去の作者・採用記録は変更しない。
各ターンの新規割当前とカタログ更新を検知した時にrouting updaterを適用し、利用可能な最新Solと必要強度を解決する。新モデルが提供確認できたらユーザーから再指定されるのを待たず、担当設定・現行スキルのモデル記述を更新し、変更を短く報告する。主担当のモデルピッカーは変更せず、現在ツールの固定役割が旧モデルを持つ場合は最新Solを明示指定できる通常ロールを使う。未提供モデルを推測で使わず、過去作品へ後継モデルを遡及帰属させない。

## 検証証拠の保存

再撮影・診断再試行は、封印前でも試行ごとの新規出力ディレクトリへ保存する。runner開始前に画像・動画・console・receiptの実書込先が前試行と重ならないことを確認する。固定名を使うrunnerは、先に前試行の全実bytesと対応ログを別試行フォルダへ保持してhashを照合し、その後に書込先を変更して実行する。画像ごとにattempt・cause・frame・target世代・寸法と取得時刻を対応付け、同名PNGを別試行のJSONへ結び付けない。上書きが起きた場合は旧bytesの欠落を明記し、残った動画・JSONと後続画像を別証拠として扱う（2026-10-08、Stun R1診断再試行でflat PNGを保持前に上書きした実行漏れ）。

試験件数・対象一覧・成功範囲は、実行したrunnerと版に結び付いた実ログから求める。派生前の概要文や手書きのTEST-RESULT件数を新runnerの実行件数として転記しない。概要と実runnerが不一致なら両方の出典を保持し、実対象を照合した追補へ訂正を記録する。封印済み概要を黙って修正せず、件数だけの一致を全対象の試験成功とみなさない。

凍結成果のhashを証跡や受渡し索引へ記載するときは、版と絶対パスを指定して実バイトから取得し、元の索引とも照合する。要約・会話内のhashは検索の手掛かりに留め、転記した値や複数版の値を継ぎ合わせた文字列をpinにしない。誤記を発見したら原記録を保持した訂正記録を作り、誤ったpinを受入根拠から外す（2026-10-05、R3 planのhashが旧版と混ざった監査記録を訂正）。

manifest・seal付き候補を「固定済み／ready」と報告した後は、作成担当も同じ版のファイルを編集しない。凍結入力に同梱されたスクリプトは、verify・audit等の名前でも実行前に書込み・子プロセス・再sealの副作用を確認する。検証は読取り専用の経路だけで行い、生成器やseal器を検証目的で元入力内に実行しない（2026-10-06、受取担当がseal-reviewを検証器と誤認して凍結索引を変更した事故）。追加修正は別の版へコピーして行い、その実byteで試験とsealを確定してから引き渡す。受取側は検証開始時に報告pinと実入力を照合し、不一致のままhostや公開候補を組み立てない。ready後の証拠追加・公開組立に着手する直前に、出力先が固定済み入力フォルダと異なることを確認する。既存版へ撮影・検査結果を追加する場合も、別の派生パッケージへコピーしてから記録器・manifest/seal生成器を実行し、元の索引を読み取り専用で保持する。担当へ追加作業を渡すときは、その派生出力先を明記する。固定後の変更が見つかった場合は旧pin・現pin・変更理由を別記録に残し、旧試験を新byteの証拠として流用しない。旧byteが失われていれば復元済みと装わない。これはハッシュで受渡しする成果物の規則であり、通常の編集中ファイルへ適用を広げない（2026-10-03、固定報告後の担当自身の追修正による再発を反映）。

凍結パッケージのbyte-hashを含む選択公開では、候補commitを作った後・push前に `git cat-file blob <candidate>:<path>` が返す生blob bufferからSHA-256とbyte長を求め、cache tokenと公開manifestのhash/byte長へ照合する。作業ツリー、index-stage表現、text-decoded command outputだけからhashを作らず、作業ツリーだけの照合でこの工程を省かない。外部stageを `hash-object` へ渡してもGitフィルタが働く場合があるため、凍結素材は版限定の `-text` と必要な `--no-filters` で元バイトを保持する。通常テキストの正規化と凍結素材のbyte-hash破損は区別し、後者を内容一致や正規化で合格にしない。deployment完了後はversion-pinned public routeのHTTP entity bodyを同じcommitのraw blobとbyte/hash/lengthで比較し、commit、取得時刻とHTTP Date、status、Content-Type、cache headers、decoded entity-body byte length、SHA-256を記録する。exact commitがdeploy中であるdeployment-state evidenceがある場合はその状態を再確認し、証拠に基づいてcontent readの再試行を判断する。古いbodyだけを根拠に機械的に再試行または合格にしない（2026-10-02、公開候補の改行変換で索引hashが不一致となった再発を反映。2026-10-05、Hover Sprint cache tokenがcommit前表現から算出された問題を反映）。

Git/API の構造化応答から content-addressed object を materialize するときは、message 等を構造化フィールドの値どおりに扱い、説明文の句読点や表示用の時刻正規化から raw bytes を補わない。ISO timestamp が UTC に正規化されていても、元 object の timezone や serialization は保持されているとは限らない。materialize 前に正確な serialization の object hash が期待値と一致することを確認し、不一致なら試行 bytes と hash を保存して ref・checkout 操作を止め、別 serialization を元 object として報告しない。

パッケージの複数のhash索引は、互いのhashを参照する循環を作らない。 seal等のdigestは実schemaと検証器で対象bytes・計算式を確認し、ファイル全体のSHAと内包するファイル一覧のdigestを同一視しない。内容manifest→そのmanifestを含むintegrity索引→外側の引き継ぎ記録など、自己参照を除いた一方向の関係を宣言し、更新後に実ファイル全体と照合する。古い索引を残したまま、内部manifestが通ったことだけで完全凍結と報告しない。除外した索引自体のhashは外側の記録で保持する（2026-10-02、Teleport r2の相互参照と古い5ファイルhashを実修正した知見）。

スクリーンショットの形式・寸法は拡張子で推測せず、実バイトの形式と対応する画像デコーダーで確認する。JPEGをPNGのIHDRとして読むなど、別形式の固定オフセットを適用しない。誤った寸法が検証済み成果に含まれていた場合は、原本・ハッシュ・帰属を保持した訂正記録を作り、その寸法を品質根拠に使わない。

AXやDOMの証拠を保存するときは、差分だけか完全な状態かを確認する。「変化なし」だけの差分を、判定内容を含む実画面証拠として扱わない。完全な観測を保存するか、その場の実際のツール出力を転記した記録であることを明示し、スクリーンショットや別端末の検証と区別する。
